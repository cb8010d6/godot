# SR/RR viewport lifetime — observed policy and untested risks

CPU review only; d29 source was not changed. No GPU, build, free call or native lifecycle experiment was performed by this review.

Absence of explicit SR/RR frees is **not sufficient to diagnose a leak**. Streamline explicitly permits lazy allocation and retention until plugin unload. Explicit deallocation is optional, non-thread-safe, and must follow completion of pending feature use. [Versioned resource-management contract](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.16/docs/ProgrammingGuide.md#28-explicit-resource-allocation-and-de-allocation), [API contract](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.16/include/sl_core_api.h#L220).

The published explicit SR and RR free callbacks release the NGX feature and erase its viewport entry immediately; RR also clears denoise/matrix parameters, while SR clears its cached output. Their free path is not the separate three-frame delayed-release path used on feature recreation. Calling it directly from a host destructor would add a new synchronization requirement. [SR free implementation](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.16/source/plugins/sl.dlss/dlssEntry.cpp#L869), [RR free implementation](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.16/source/plugins/sl.dlss_d/dlss_dEntry.cpp#L1164).

Current host observations:

- `DLSSContextInner` destroys only initialized NIS feature state, releases its NIS texture RIDs, then immediately recycles the viewport number. SR/RR retained feature state can therefore survive into a different host context reusing that number. This can be a bounded cache policy, not automatically unbounded growth.
- Published RR auto-reset handles first allocation, mode/output/layout/preset changes. A same-size reused ID may keep an existing feature handle; a camera cut or scene change is not necessarily visible to that automatic test. Explicit history invalidation and resource reclamation are separate concerns. The first-reset/ID-reuse risk remains **unmeasured**, and cannot explain the fresh-process one-viewport F-preset red test by itself.
- Forward-clustered buffer cleanup currently `memdelete`s the context. Driver callbacks refer to that context through userdata. A replacement retirement scheme must keep any still-queued CPU callback ownership valid as well as waiting for GPU work; elapsed time or a render-thread message alone proves neither.
- RD's per-frame typed dispose queues run after that frame slot's fence wait in `_begin_frame`; there is no existing generic external-free callback queue in the checked RD API. Adding one would affect core headers and shutdown ordering. In current `RenderingDevice::finalize`, all host work is drained, then Streamline is shut down before the later pending-RID disposal loop. A new deferred SDK-free callback cannot simply be appended to that later loop and retain unloaded function pointers.
- Main-queue frame fences are not by themselves proof for SDK-owned FG/presentation queues. Existing terminal cleanup specifically performs a backend wait before process-wide SDK shutdown. It should remain terminal, not be repurposed into an unconditional per-frame stall.

Recommended current action: retain the SDK's legal lazy policy and the already tested d29 build. Record ID-reuse/history/VRAM-reclamation risks separately. Do not add bare destructor frees, a frame-count-only delay, monotonic never-reused IDs with retained per-ID allocations, or a stall every frame.

A future narrow measured slice should first log context/viewport creation and reuse, exercise SR/RR scene teardown/recreation at identical sizes and camera cuts, compare the first evaluated frames against an explicitly reset control, and observe repeated-cycle memory reaching a plateau or not. A first-evaluation-per-feature reset state machine could address a demonstrated reused-history issue without changing the optional caching policy, but is not yet a measured fix here.

If explicit reclamation proves necessary, the safe design needs a render-thread retirement queue with actual completion proof, deferred ID reuse, separately tracked attempted/initialized SR/RR/NIS features, and a shutdown drain before SDK unload. Preserve error results; never call unloaded/unavailable plugins or report an absent allocation as an established free. Validate FG-enabled lifecycle separately before promising it is unchanged. This framework-level retirement design is intentionally not implemented in the current slice.
